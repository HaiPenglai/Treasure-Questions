# 宝藏论文链接整理任务

你需要完成以下任务：

## 任务目标

维护 `宝藏论文链接大全/papers.json`，为《每天一个宝藏论文》系列视频补充对应的论文链接（优先 PDF 直链）。

**核心原则：论文名优先从封面读，不从标题猜。** 每期视频的第一帧（即 `assets/papers/{bvid}.jpg`）必然是论文标题页，顶部印有论文的**英文原题**。因此确定"这期讲的是哪篇论文"这件事，应以封面为权威信源，视频标题大部分时候只用来判断"这期讲了几篇论文"。这样的好处是：只要封面标题准确、论文链接真实存在，就不需要再人工核对论文与视频的对应关系。

---

## 执行步骤

### 步骤1：更新视频列表

运行根目录下的封面提取脚本，确保 `README.md` 和视频信息是最新的：

```bash
python bilibili_cover_extractor.py
```

该脚本会：
- 从 B 站获取最新发布的视频列表
- 更新 `bv_list.json`
- 自动刷新 `README.md`

#### 封面清晰度检查（必须执行）

- 封面像素下限为 **1,500,000 像素（1.5 MP，宽 × 高）**，不是 1.5 MB 文件大小。旧高清封面通常为 1728×1080（1.87 MP）或 1920×1080（2.07 MP）；JPEG 字节数受内容和压缩影响，不能据此判断清晰度。
- 脚本会检查已有图片，自动重试低于下限或损坏的封面；视频流按实际分辨率选择最高质量。新图片必须通过解码和像素检查才会替换原图，禁止用插值放大冒充高清。
- **Agent 必须检查输出中的 `[Quality WARNING]` 和失败统计**。若有低清封面，必须向用户列出 BVID、标题/期数、实际尺寸及是否重下成功；若仍不达标，不得宣称封面更新已全部完成，也不得据模糊封面猜论文标题。
- 登录过期/未登录可能使 B站仅返回 480p：768×480（0.37 MP）或 852×480（0.41 MP）。此时先检查登录状态，运行 `python login_bilibili.py`，需要扫码就提醒用户；登录成功后重跑封面脚本。若登录有效仍低于下限，检查源视频是否仅提供低清流，并明确告知用户。
- 2026-11-10 排查：从问题第 271 期开始，同期问题/动画/论文共 28 张封面为 480p，其余 471 张均不低于 1.5 MP。第 271 期实测有效登录可取得 1728×1080，匿名仅可取得 768×480；支持登录失效导致清晰度回落的判断。旧脚本只取流列表第一项且无像素校验，低清图保存后又因“已存在”被永久跳过。仅重下封面时，不得修改已整理好的 `宝藏论文链接大全/papers.json` 及其生成文档。
- 本次修复结果：28 张低清封面已全部重下为 1080p，并补齐问题 285–287 期及论文 216–218 期的 6 张新封面；全库 505 张封面均达到下限。471 张原有高清图及整个 `宝藏论文链接大全` 目录通过 SHA-256 核验，内容未变。

### 步骤2：定位新增的宝藏论文

`README.md` 内容很长，包含宝藏问题、宝藏名词、宝藏论文、宝藏实验等多个板块。**不要从头读**，也不要直接在文件里搜索 `## 每天一个宝藏论文`。

**正确做法：**
1. 先执行步骤1，确保 `bilibili_cover_extractor.py` 已运行，此时 `README.md` 相对于上一次 commit 已发生变更
2. 使用 git 命令只查看 `README.md` 中 `【每天一个宝藏论文】` 板块的变更：

```bash
git diff HEAD -- README.md | grep -E "^\+.*###.*【每天一个宝藏论文】"
```

3. 输出中以 `+` 开头的行就是本次新增的宝藏论文视频标题。从标题中提取 `video_id`，并借此判断这期是**单篇**还是**多篇**论文；这些就是本次需要补充论文链接的条目。

> 注意：视频标题在这里**只用于取 `video_id` 和判断论文篇数**。这期到底讲的是哪篇论文，**不要从标题猜**，留到步骤4 读封面确定。

**原理：** 所有比上一次 commit 新增的 `【每天一个宝藏论文】` 视频，即为待补充论文链接的视频。

### 步骤3：对照已有数据，找出缺失项

读取 `宝藏论文链接大全/papers.json`，与步骤2中读到的最新宝藏论文进行对照。

**对照逻辑：**
- `papers.json` 按 `video_id` 倒序排列
- 比较 `video_title` 或 `video_id`，找出 `papers.json` 中**还没有**的宝藏论文
- 这些就是本次需要补充的论文

---

### 步骤4：读封面拿原题，按原题搜索论文链接

对步骤3 找出的每一个缺失条目，按以下顺序执行：**先读封面拿到论文英文原标题，再用原标题搜索链接，最后把搜到的标题和封面原题比对**。

#### 第一信源：直接读论文封面拿原题

步骤1 下载封面时，宝藏论文的视频封面统一落在 `assets/papers/{bvid}.jpg`（文件名就是 BVID）。**这就是本期论文的标题页**，直接读取该图片，把顶部的英文论文原标题记住，随后用这个原标题去搜索链接。

因为拿到的是论文的**准确英文全名**，搜索时定位到的论文只有唯一解，不再有"从中文标题反推英文名"可能猜错、或猜出多篇候选的风险。

**执行要点：**

- 只读**本次新增**视频的封面即可。封面本来就在步骤1 随流程下载，不存在额外下载成本
- 封面顶部那行英文就是完整原题，请**逐字记住**，不要顺手简化或意译

#### 第二信源：视频标题（补充用）

视频标题不再用于"猜论文名"，主要负责两件事：

1. 判断这期是**单篇**还是**多篇**论文（标题含"读N篇""论文串讲"等字样的属于多篇）
2. **补充封面未覆盖的论文**：**封面通常只印一期的主论文**，若标题里还点名了其他论文（例如标题写"DSA 稀疏注意力及其3篇最新改进工作"而封面只有主体模型那篇），这部分仍需按标题去搜索补充

#### 特殊回退：封面没给出标题时，只能靠标题反推

极少数情况下，封面里根本没有论文标题（比如：放了插图页、标题截图被截断了），这时唯一的线索就是视频标题：

- 用视频标题里的关键词去反推论文。例如从"DSA 稀疏注意力"推测是 DeepSeek 那篇重要论文，去找到并下载那篇论文
- 反推出来的论文**同样要按下面「关键校验」验证**，并在最终汇报中**明确标注这是标题反推得到的**，不是封面直接读到的
- 用标题实在无法确定是哪篇 → 按「不留空规则」处理（先补全其他论文），并在汇报中说明

#### 关键校验：搜到的标题必须和封面比对

搜到链接后，把搜索结果里的论文标题**与封面原题逐字比对**。

- **完全一致**（或仅断行差异这种）→ 正常写入
- **存在实质差异**（不是同一篇或只是主题相近的另一篇）→ 看看能否找到一模一样的，优先再试试。如果确实找不到，找到最接近的，**填入最接近的**（例如只是版本不同，这其实可以接受），并在最终汇报中单独列出，格式如：
  `大部分标题和封面原题逐字一致，但是：[188] 封面标题「X」与搜到的最接近的「Y」不一致/封面没有展示标题/有多篇论文， 填入了最接近的「Y」。请问是否需要调整？`

> 这一步是本流程的质量闸门：**封面保证"论文与视频的对应关系"，校验保证"链接真实存在"**。用户只需确认论文本身真实存在即可。

#### 搜索与链接优先级

搜索工具使用 `web_search` / `web_fetch`，检索词用"封面英文原题 + `arxiv pdf`"。

1. `https://arxiv.org/pdf/xxxxx.pdf`（PDF 直链，最优）
2. `https://arxiv.org/abs/xxxxx`（arXiv 摘要页）
3. 官方 PDF、HuggingFace resolve 直链、USENIX/NeurIPS 等会议官方 PDF

**链接必须实际验证**（不能只看搜索结果里的标题）：确认能取回真实 PDF（响应体以 `%PDF-` 开头），且页面上标注的论文标题与封面原题一致。DOI 页、出版社摘要页、技术博客在无 PDF 时可用，但要在汇报中说明。

#### 不留空规则：交及格答案，好过交白卷

**不要用空字符串占位。** 与其留一条 `paper_link: ""` 让用户自己再去查，不如给出你能找到的最接近的论文，并说明它的不确定性。

- 搜到的标题与封面原题**有差异、但能判断是同一篇**（例如只是版本、年份不同）→ **填入它**，并在汇报中说明差异
- 搜到的只是**主题相近的另一篇** → 先按上面「关键校验」再试几轮换关键词搜索；若确实找不到完全一致的，**填入最接近的那篇**，并在汇报中说明它是替代项
- 只有**连最接近的都选不出来、完全无法判断是哪篇**时，才允许留空 —— 并在汇报中明确说明原因

> 一句话：每个条目都要交出论文链接；留空是最后手段，不是省事的默认选项。

### 步骤5：写入数据并生成文档

将搜索结果整理为标准的 JSON 格式，追加到 `papers.json` 中：

```json
{
  "video_id": 27,
  "video_title": "[27] XXX论文解读【每天一个宝藏论文】",
  "bvid": "BVxxxxxxxxxx",
  "papers": [
    {
      "paper_title": "论文完整标题",
      "paper_link": "https://arxiv.org/pdf/xxxxx.pdf"
    }
  ]
}
```

**注意事项：**
- 一个视频可能对应**多篇**论文（如综述+数据集、读3篇论文等），`papers` 数组中需列出所有论文
- 新条目按 `video_id` 降序插入到 `papers.json` 的合适位置（保持倒序）
- 写入后运行 `宝藏论文链接大全/generate_readme.py` 重新生成 `README.md`

---

## 并行策略

如果本次需要搜索的论文数量**超过 10 篇**，不建议由单个 Agent 独自完成。

**分发规则：**
- **先由主 Agent 顺序读完所有新视频的封面**，记录每个视频对应的英文原题
- 再把"封面原题 + 视频标题"打包分发给 SubAgent 去搜索，每组不超过 10 个视频
- 启动多个 SubAgent 并行搜索，**每次最多启动 4 个 SubAgent**
- 每个 SubAgent 负责自己的分组，返回标准 JSON 格式结果
- 汇总所有 SubAgent 的结果后，统一写入 `papers.json`

**重要：封面图片不要交给 SubAgent 去读。** 图片是视觉附件，SubAgent 拿不到主 Agent 手上的图片上下文，分包读取很容易互相干扰、重复读或读错。让主 Agent 一次读完全部封面（默认只有十几个视频，成本可控），SubAgent 只负责"拿着已知原题搜链接"这一件事。

**SubAgent 任务示例：**
```
你的任务是搜索以下宝藏论文视频中提到的论文链接，返回严格的 JSON 数组。
每个视频我都已从视频封面（论文标题页）读出了论文英文原题，原题是权威信源，
请直接用它搜索，并把搜到的标题与原题逐字比对；若不一致必须在 NOTES 中说明。

1. video_id: 188, video_title: "[188] XXX论文解读", bvid: BVxx
   封面原题：Scaling and evaluating sparse autoencoders

2. video_id: 187, video_title: "[187] 读2个XXX的论文", bvid: BVxx
   封面原题：<封面只有主论文，标题里还提到的另一篇需按标题搜索补充>

返回格式：[{"video_id": ..., "video_title": ..., "bvid": ..., "papers": [{"paper_title": ..., "paper_link": ...}]}]
```

## 格式规范

### papers.json 字段说明

| 字段 | 类型 | 说明 |
|------|------|------|
| `video_id` | int | 视频序号，如 26 |
| `video_title` | str | 视频完整标题 |
| `bvid` | str | B 站 BV 号，如 BV1Bcd2BeEVv |
| `papers` | array | 该视频解读的所有论文列表 |
| `papers[].paper_title` | str | 论文完整标题 |
| `papers[].paper_link` | str | 论文链接，优先 PDF 直链 |

### 生成后的 README.md 格式

运行 `generate_readme.py` 后，每个视频条目格式如下：

```markdown
### [26] GQA：分组查询注意力论文解读【每天一个宝藏论文】
- 观看视频：[BV1Bcd2BeEVv](https://www.bilibili.com/video/BV1Bcd2BeEVv)

- 阅读论文：[GQA: Training Generalized Multi-Query Transformer Models from Multi-Head Checkpoints](https://arxiv.org/pdf/2305.13245.pdf)

---
```

## 任务完成后的 Git 提交

完成 `papers.json` 更新并重新生成 `README.md` 后，请依次执行以下三条指令将改动提交到 GitHub：

```bash
git add .
git commit -m "update: add paper links for videos 73-80"
git push
```

> 说明：`git add .`、`git commit -m`、`git push` 这三种操作非常安全，已经执行过很多次。
> 注意：如果 `git push` 提交失败，可以试试不用代理重新`git push`试试，**但不要**执行任何其他 git 操作（如 `git pull`、`git merge`、`git rebase` 等），请直接向用户汇报失败信息。
